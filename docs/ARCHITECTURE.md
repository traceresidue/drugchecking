# Architecture

How the drugchecking repository fits together: the production data flow, the data model, and the visualization framework internals. For the expansion plan (JS/React, spectral pipeline, SQLite librarian), see [ROADMAP.md](ROADMAP.md).

## System overview

```
  ┌────────────────────┐   ┌──────────────────────────┐   ┌───────────────────────────┐
  │ COMMUNITY SAMPLES  │   │ UNC LAB (GC–MS Orbitrap) │   │ THIS REPO (distribution)  │
  │ mail-in kits +     │──▶│ Xcalibur + SWGDRUG /     │──▶│ datasets/*.{csv,dta,      │
  │ collection card    │   │ Cayman / NIST 20 libs    │   │   xlsx,v8xpt}             │
  └────────────────────┘   └──────────────────────────┘   │ spectra/<id>.PNG          │
                                    │                     │ chemdictionary/           │
                           Stata .do pipeline             └─────────────┬─────────────┘
                           (datasets/code/*.do:                         │
                            result_processing,               ┌──────────┴──────────────┐
                            categorize, autotext)            ▼                         ▼
                                                   ┌────────────────────┐   ┌────────────────────┐
                                                   │ CONSUMERS          │   │ VISUALIZATIONS     │
                                                   │ analysts (raw CSV  │   │ Streamlit apps     │
                                                   │ via GitHub URLs),  │   │ (live CSV reads),  │
                                                   │ streetsafe.supply  │   │ viz-framework      │
                                                   │ results browser    │   │ (static build)     │
                                                   └────────────────────┘   └────────────────────┘
```

Key property: **GitHub is the distribution layer.** Raw CSVs are consumed directly via `raw.githubusercontent.com` URLs by dashboards, spreadsheets, and third parties. File paths are a public API — renaming or moving dataset files breaks downstream consumers.

## Components

### 1. Datasets (`datasets/`)

Produced by the lab's Stata pipeline (`datasets/code/*.do`), published in four formats each (`.csv`, `.dta`, `.xlsx`, `.v8xpt`):

- **`analysis_dataset.*`** — WIDE, one row per sample. Card metadata, geocoded geography (OpenCage; county FIPS with leading zeros, `state_county` like `NC | NEW HANOVER`), and ~100 derived flags. Naming convention: `lab_<substance>` = detected as primary; `lab_<substance>_any` = primary or trace.
- **`lab_detail.*`** — LONG, one row per (sample, substance). Standardized `substance` name plus PubChem CID / CAS / UNII, `method` (GCMS), `abundance` (blank = primary, `trace`), and class flags carried from the chemical dictionary.
- **`labservice/unc_gcms.*`** — public confirmatory/complementary GC–MS results; multiple rows per sample; includes `gcms_peak` retention time. No geographic identifiers.
- **`selfservice/<PROGRAM>/`** — per-program cuts of the two core files (AC, DN, HC, NV, OR, TN, WA, hnc, nys). `nc/` holds the North Carolina cut.
- **`program_dashboards/elements/`** — small pre-aggregated CSVs (counts, purity, recently-detected) generated by `.do` scripts for embedding in program dashboards.

### 2. Chemical dictionary (`chemdictionary/`)

The source of truth for substance identity. One row per substance ever detected: standardized name, PubChem CID, CAS, UNII, pronunciation, `commonrole`, and 1/0 columns per drug class (a substance can belong to several). New substances are added when first detected and classified by lab expertise + literature. All class flags in the datasets trace back here.

### 3. Spectra (`spectra/`)

~800 chromatogram images named `<sampleid>.PNG`. These are **rendered images, not structured spectral data** — the underlying mzML/raw instrument files are not in the repo. Peak labels live in the human-readable record at `streetsafe.supply/results/p/<sampleid>`.

### 4. Documentation (`docs/`, `datasets/technical_details.md`)

- `lab_methods.md` — citable materials-and-methods text (instrumentation, derivatization, libraries used).
- `confirmatory.md` — when FTIR programs should send samples for GC–MS confirmation.
- `toxexposureassessment.md` + `tox_assessment.csv` — toxicology exposure framework.
- `notebooks/` — example Jupyter analyses (pandas + plotting) against the public CSVs.
- `graphics/data flow/` — schematic diagrams of the chemistry/epi/software workflow.

### 5. Streamlit dashboards (`datasets/code/Streamlit/`)

Multi-page Streamlit app (`Home.py` + `drug_market.py`, `ncxylazine.py`, `overdose.py`, `psychedelics.py`, `stimulants.py`) that reads the published CSVs and renders public dashboards, harm-reduction handouts, and program-specific views.

### 6. Visualization framework (`visualization-framework/`)

33 standalone HTML visualizations across MS, GC–MS, FTIR, supply-trend, geographic, result-communication, sonic, and experimental categories. Design goals: offline-first (opens via `file://`, no CDN), accessible (WCAG 2.1 AA targets), harm-reduction framed.

Build internals:

```
src/registry.json      metadata per viz: id, n, category, title, libs, data slices
src/<id>.js            per-viz logic (D3 / Plotly / WebAudio), assumes window.DCF + window.DATA
viz/_shared.js         design system: TOKENS palette, classify() substance→class,
                       spectral synthesis (chromatogram/stickSpectrum/ftirCurve),
                       fmt helpers, tooltip, scaffold. ES module, inlined at build.
data/aggregates.json   real aggregates from 6,580 samples (top substances, monthly trends,
                       co-occurrence, geo, retention times, emergence, embeddings)
data/spectra.json      illustrative MS/FTIR/chromatogram spectra (labeled as such)
build.py               inliner: _shared.js (globalized) + data slices + src/<id>.js
                       → viz/<id>.html, fully self-contained; adds nav header + auth guard
viz/lib/               vendored d3, d3-sankey, plotly, smiles-drawer, topojson-client
test/check.js          Playwright: every page must load with zero console/page errors
```

Deployment: `vercel.json` runs `build_index.py` which generates a password-gated `index.html` (password from `MAIN_PASSWORD` env var; the generated file is gitignored). Each viz page checks `localStorage.dcf_auth` and redirects to the gate.

**This gate is a client-side visibility deterrent, not access control.** `MAIN_PASSWORD` is inlined in plaintext into `index.html`'s JS (visible via view-source/devtools), and the per-page check (`localStorage.getItem('dcf_auth')`) can be satisfied from any browser console in one line, without ever knowing the password. It stops casual browsing and search indexing; it does **not** protect embargoed, private, or otherwise sensitive data. For real protection, use Vercel's server-side [Deployment Protection](https://vercel.com/docs/deployment-protection) (password protection or Vercel Authentication/SSO) — configured in the Vercel dashboard, CLI (`vercel project protection`), or REST API, not in `vercel.json`. See "Future option: Vercel Deployment Protection" below.

**Future option: Vercel Deployment Protection.** If real access control is ever needed (e.g. to show embargoed/private results), Vercel offers server-side protection that would supplement or replace the `build_index.py` gate: Password Protection or Vercel Authentication (SSO), enforced at the edge before a request ever reaches this app, so it can't be bypassed from devtools the way the current gate can. This is **not** a `vercel.json` field — there is no code-level equivalent — it's set per-project via the Vercel dashboard (Project Settings → Deployment Protection), the CLI (`vercel project protection enable <project> --password`), or the REST API (`passwordProtection` / `ssoProtection` on the project). Password Protection requires an eligible (paid) plan. This has not been enabled; it's left here as a pointer for whoever owns the Vercel project to turn on if/when it's needed. Automated tooling (CI, Playwright in `test/check.js`) would need the bypass mechanism Vercel provides for protected deployments (`VERCEL_AUTOMATION_BYPASS_SECRET` / `x-vercel-protection-bypass` header) if protection is turned on.

### 7. Stata production code (`datasets/code/`, `textexport/`)

`result_processing.do` and `categorize.do` transform raw lab exports into the published datasets; `autotext.do` generates plain-language result narratives; `listofdrugs.do` maintains the druglist. These run in the lab's environment (not CI) — the repo receives their outputs.

## Data model

```
                       chemdictionary.csv
                       (substance → classes, CID/CAS/UNII)
                              │ standardizes / classifies
                              ▼
  analysis_dataset ◀──── sampleid ────▶ lab_detail ────▶ unc_gcms (labservice)
  1 row / sample                       1 row / sample-substance
       │                                                  │
       ▼                                                  ▼
  spectra/<sampleid>.PNG                    streetsafe.supply/results/p/<sampleid>
  (chromatogram image)                      (human-readable, peak-labeled record)
```

## Known gaps (addressed in ROADMAP.md)

1. **Spectra are images.** No machine-readable GC–MS/FTIR spectral data (mzML, MSP, JCAMP-DX) — the viz framework synthesizes illustrative spectra instead of drawing real ones.
2. **Static visualization data.** `aggregates.json` is a build-time snapshot; no refresh pipeline connects the live datasets to the framework.
3. **No sample index/explorer.** There is no way to browse, select, and load specific real samples into the visualizations.
4. **Toolchain split.** The viz framework is hand-rolled JS built by a Python inliner; there is no JS package management, module system, or React capability for stateful apps.
5. **Disparate formats.** Each external drug-checking data source (DrugsData, Toronto DCS, WEDINOS, reference libraries) uses different formats; nothing ingests them.
